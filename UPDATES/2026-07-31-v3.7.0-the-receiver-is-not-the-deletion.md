## What This Is

A security fix. **If you installed any version from v3.3.0 through v3.6.0, your Permanent Floor deletion gate can be walked past, and you should apply this update.**

Five ways of deleting a protected file through Node were allowed. One nearly identical way was blocked. The gate was matching the name of the thing holding the function rather than the function being called.

The rest of the release is two checkers that were reporting a fresh vault as broken.

## The Defect

Since v3.3.0 the gate has blocked Node deletions with this test:

```sh
grep -qE '(fs\.unlinkSync|fs\.rmSync|fs\.promises\.unlink|fs\.promises\.rm)[[:space:]]*\('
```

Read it closely. It requires the literal characters `fs.` before the method name. That is a fact about how the script happened to be written, and it is not a fact about deletion. Every one of these deletes the same file, and only the first was refused:

```js
const fs = require('fs'); fs.unlinkSync('notes.md')       // blocked
require('fs').unlinkSync('notes.md')                       // allowed
const f = require('fs'); f.unlinkSync('notes.md')          // allowed
const { unlinkSync } = require('fs'); unlinkSync('notes.md')  // allowed
const f = require('fs'); f.rmSync('notes.md')              // allowed
const f = require('fs'); f.promises.unlink('notes.md')     // allowed
```

The gate asked what the receiver was called. Rename the receiver and the Floor consents.

This is the same shape as the v3.3.1 hole, one level in. That one classified on the command string instead of the target path. This one classifies on the spelling instead of the act. Both read as correct.

**The positive control passed the whole time.** `floor-gate-selftest.mjs` carried exactly one case for this door, and it spelled the receiver `fs.`, so it exercised the single form that worked. A green suite for two releases, over five open doors. A guard is verified by firing. This release is the reminder that it matters *what* you fire.

## The Fix

Match the method, never the receiver.

```sh
grep -qE '(^|[^A-Za-z0-9_$])(unlinkSync|rmSync)[[:space:]]*\(|\.promises[[:space:]]*\.[[:space:]]*(unlink|rm)[[:space:]]*\('
```

The leading character class is load-bearing. `rmSync` is a substring of `performSync` and of `confirmSync`, so a bare alternation would refuse ordinary code and trade a hole for a wall. Requiring a non-identifier character before the method name means the guard fires on a call and stays quiet on a coincidence.

The second branch covers the promises API reached through any handle.

The target test that follows is unchanged. A protected extension must still appear in the command for the gate to refuse, so deleting a build log through Node is allowed exactly as before.

## The Specification, If You Have Customized Your Copy

Do not apply this as a patch. Your gate may have moved. Apply the intent:

1. In `pre-tool-approval-gate.sh`, find the branch that blocks Node deletions. It is the one whose message names `fs unlink`.
2. Change its condition so it matches the **method name** with a non-identifier character before it, rather than a fixed `fs.` receiver. Cover `unlinkSync`, `rmSync`, and `.promises.unlink` / `.promises.rm` reached through any handle.
3. Leave the protected-extension test that follows untouched.

## The Test That Proves It

`floor-gate-selftest.mjs` gains five must-block cases, one per spelling above, and three must-pass cases covering `performSync(`, `confirmSync(` and an unlink of a file the Floor does not protect. The must-pass cases matter as much as the others. Widening a match is the change most likely to buy a closed door with a wall.

Run it. On an unpatched copy it fails five cases and names each open door. On a patched copy it reports 29 of 29.

```sh
node "Council Chamber/scripts/hooks/floor-gate-selftest.mjs"
```

**Run it before you apply the fix as well as after.** A test that passes on the broken copy is testing the wrong thing, and that is precisely what happened here.

## The Second Half: Two Checkers That Failed on Day One

`check-skill-mirrors.mjs` compares your canonical skills against the copies your AI interface reads. On a fresh clone it reported every skill as drift and exited 1, because a fresh clone has no interface directory at all. Links are local filesystem objects and git does not carry them. You create them in Session 1.

So the first thing this template told a new reader was that it was broken. A check nobody trusts is a check nobody reads.

It had a second failure that outlives day one. It demanded a mirror under **both** `.claude/skills` and `.codex/skills`. A reader running one interface, with every skill correctly linked, still got a wall of errors for the interface they had chosen not to use.

Both are fixed by one rule: **a mirror root that does not exist on disk is a runtime this vault does not use, never drift.** When none exists, the checker prints what it found, points at Session 1 and exits 0. When one exists, it is checked normally and a missing link inside it is still real drift.

This checker had never had a positive control. It has one now, `check-skill-mirrors-selftest.mjs`, four cases against fixture vaults built in a temp directory: a fresh vault, a fully linked vault, a vault missing one link, and a vault whose mirror content has fallen behind. Teaching a detector when to stay quiet is exactly the change that can turn it into a detector that never speaks, so the quiet cases and the loud cases are both proven.

## Added

- `Council Chamber/scripts/check-skill-mirrors-selftest.mjs`, the positive control described above.
- Two CI steps firing it, plus the checker itself on the fresh checkout, so the day-one path is proven on a real clone rather than only on a fixture.

The list had said seven and held seven while nine were true. A count restated beside the list it counts will eventually disagree with it, so the list is now its own count.

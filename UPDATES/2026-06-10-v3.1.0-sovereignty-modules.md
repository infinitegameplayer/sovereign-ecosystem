## What This Is

Four sovereignty modules. Each one extends what the ecosystem can reach without changing the spine that already works.

External work can now route to a verified set of secondary model providers. Long-form prose gets a canonical anti-AI editing pass. The Obsidian vault can connect to the AI interface as a live context source. And a documented path opens toward offline inference and semantic search for Sovereigns building toward a lower-cloud setup.

The theme is the same across all four. Each is a door, not a default. The template runs complete without any of them. You open the one that fits when it fits.

## What It Adds / Changes

### 1. External Model Routing module

A new layer for dispatching deterministic, no-judgment work to secondary model providers. Voice-bound and judgment-bound work stays on the primary interface. This layer is additive and the primary provider path is untouched.

- **External Model Routing Codex** at `Council Chamber/Codices/External Model Routing Codex.md`. The single source of truth for which external providers exist in the infrastructure, what they cost, what they can do and which routing slots they fit. It ships in template form. Four providers are in scope: OpenRouter, NVIDIA NIM, DeepSeek and Groq. The codex carries:
  - **A provider table with env-var slots.** Each provider has its own account, its own key acquisition flow and its own slot in `scripts/.env` (`OPENROUTER_API_KEY`, `NVIDIA_NIM_API_KEY`, `DEEPSEEK_API_KEY`, `GROQ_API_KEY`). Keys live in the gitignored `.env` and never enter version control. A payment-method gate notes that a working key does not guarantee functional dispatch. Signup, key acquisition and dispatch are three distinct gates.
  - **A Worker-Eligible Task Taxonomy.** The split principle: gather stays on the orchestrator, synthesize routes to the worker, verify returns to the orchestrator. A five-condition eligibility test gates any task class before it routes out. Worker-eligible classes ship as template placeholders, verified before first use.
  - **Model Era Notes.** Integration realities for current frontier APIs. Refusal arrives as an HTTP 200 with `stop_reason: "refusal"`, so a handler that checks only the status code treats a refused request as success. Thinking is always on at the newest tier and depth is set through the effort parameter, not by disabling thinking. A server-side fallbacks parameter and a native memory tool round out the notes.
- **`scripts/external-worker.mjs`.** The single dispatch entry point and the template's first API-calling script. It is parameterized by `--provider`, `--model`, `--prompt` and an optional `--context-pack`. It reads credentials from `scripts/.env`, dispatches via each provider's OpenAI-compatible or Anthropic-compatible endpoint, auto-injects the Ṣāḍguṇya ambassador orientation per the Ambassador Doctrine, logs dispatch metadata and fails loud on missing keys or rate-limit errors. A refusal exits with a distinct code rather than passing as a silent success.
- **A CLAUDE.md Operational Efficiency dispatch line.** The standing rule that names the boundary. Deterministic no-judgment work routes to external providers through the script. Voice-bound and judgment-bound work stays on the primary interface. The codex holds the provider catalog, the taxonomy and the rate-limit discipline.

This is the first time the template ships a script that calls a model API. The codex and the script arrive together so the boundary is named before the first dispatch lands.

### 2. Manuscript Anti-AI Edit Pass skill

A new Expression-aligned skill at `Council Chamber/Skills/Manuscript Anti-AI Edit Pass/`. It runs the canonical anti-AI editing pass over a long-form manuscript: a book chapter, an ebook, a multi-chapter playbook or any long-form digital product.

- **It loads the Anti-AI Writing Patterns Codex** that shipped in v2.8.1 and sweeps the target text in phases. Mechanical lexical scans run first. Judgment-heavy structural and voice passes run after, with the voice pass loading the Writing Style Codex voice anchor before it judges.
- **It assembles a structured edit packet** organized by category and yields for review. The skill flags and proposes. It does not rewrite passages wholesale and it does not auto-apply on the judgment passes. Approved edits are applied through the Edit tool, then a verification pass confirms the fixes landed without introducing new tells.
- **Surface-then-approve is the default.** A mode exists for auto-applying the two mechanical categories, but the skill does not proceed past the judgment passes without input.

The skill is Expression-aligned. It links the Anti-AI Writing Patterns Codex and the Writing Style Codex, and it sits in the same expression lineage as the codex it sweeps against.

### 3. Public library wave

The Manuscript Anti-AI Edit Pass also ships as a standalone installable plugin in the Infinite Game OS public library at infinitegameos.io as `anti-ai-edit-pass`.

This is dual-distribution. The skill stays in the Foundation as part of the full experience and also installs as an individual plugin for anyone who wants that one door. Four skills already shipped this way: Source Harvest, Self-Healing, Session Closeout and Playwright. Anti-AI Edit Pass joins them, making five. The template remains the complete system. The plugins are individual entrances for people who want a piece before the whole.

### 4. Getting Started Optional Paths

Two new optional paths join the Getting Started folder. These are infrastructure, not modules. They open after the Foundation loop is already stable.

- **Optional Path - Obsidian MCP Bridge** at `Getting Started/Optional Path - Obsidian MCP Bridge.md`, paired with `.mcp.json.example` at the repo root. The bridge connects the Obsidian vault directly to the AI interface through the cyanheads/obsidian-mcp-server and the Obsidian Local REST API plugin. With it, the vault becomes a live context source the interface can read, search, create and edit, rather than only what you paste into chat. The posture is read-only by default. Three controls govern a well-configured bridge: scope to one vault, a read-only starting allowlist and an explicit features list. Writes unlock through a deliberate choice, never as a default.
- **Optional Path - Local Inference and Semantic Search** at `Getting Started/Optional Path - Local Inference and Semantic Search.md`. Documentation only. Two layers, both rooted in the same principle that the vault stays the source of truth:
  - **Local inference fallback via Jan.ai.** An open-source desktop application that runs language models locally and exposes an OpenAI-compatible API at `localhost:1337`. The fit is mechanical work and offline operation, not voice or judgment. Any ecosystem script written to accept an endpoint override can point at the local server when the primary provider is unavailable.
  - **An optional semantic search layer.** A memsearch option (Milvus-backed, installable as a plugin) and a sovereignty-preferred local variant (SQLite plus a locally running embedding model). In both, Markdown stays canonical and the vector index stays a rebuildable cache, never the store of record.

The Optional Paths Selection and Conversion selector now lists the Local Inference path alongside the existing optional paths.

## How to Implement

### The External Model Routing module

1. Pull the three pieces: `Council Chamber/Codices/External Model Routing Codex.md`, `scripts/external-worker.mjs` and the CLAUDE.md Operational Efficiency dispatch line.

2. Read the codex before configuring anything. It names which providers are in scope and what each fits.

3. Create accounts and add keys to `scripts/.env` only for the providers you intend to use. The Sovereign can pause after any provider. No model calls happen at the key-acquisition step.

4. Run a first dispatch through the script once a key is configured:

   ```
   node scripts/external-worker.mjs --provider groq --model llama-3.3-70b-versatile --prompt "..."
   ```

5. Verify the provider before promoting it to active use. The codex carries a six-item verification checklist per provider. A configured key is not a verified provider.

### The Manuscript Anti-AI Edit Pass skill

1. Pull the skill at `Council Chamber/Skills/Manuscript Anti-AI Edit Pass/`. It depends on the Anti-AI Writing Patterns Codex from v2.8.1 already being present.

2. Invoke it after a manuscript draft is complete, or let a Pending Plan handover map name it at the edit phase. Pass a `target_path` to the manuscript file or directory.

3. Review the edit packet it surfaces. Approve, modify or reject each finding. The skill applies only what you approve.

### The Obsidian MCP bridge

1. Install the Obsidian Local REST API community plugin and copy its API key.

2. Copy `.mcp.json.example` to `.mcp.json` at the repo root and fill in the API key. Confirm `.mcp.json` stays out of version control. The `.gitignore` excludes it by default.

3. Keep Obsidian open with the plugin enabled, start a session, and verify the interface can list your vault tags or retrieve a known note. Start read-only. Expand to writes only after the read-only connection proves stable.

### The local-inference path

1. Read `Getting Started/Optional Path - Local Inference and Semantic Search.md`. Decide which layer, if either, is applicable now.

2. Convert any applicable layer into its own Pending Plan with setup steps scoped. Leave it documented and unimplemented if neither feels urgent. The path is a door, not a default.

## Optional?

The codex, the script and the dispatch line ship to the template as core surfaces. The external dispatch layer itself is only as active as the keys you choose to configure. Add no keys and nothing changes. The primary provider path runs exactly as before.

The Manuscript Anti-AI Edit Pass is a Foundation skill. It activates when you invoke it, not before.

The Obsidian MCP bridge and the local-inference path are Getting Started Optional Paths by nature. They open after the Foundation loop is stable, when the live vault connection or the offline capability fits the work in front of you.
